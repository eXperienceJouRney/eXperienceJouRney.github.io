5.5 银行家算法

有序资源分配法用「规定申请次序」来破坏环路条件，但它要求进程的实际使用顺序服从资源编号。还有一条更宽松的路：不规定次序，而是在每次分配之前先算一算「这笔资源给出去以后，系统还安不安全」，不安全就不给。这就是银行家算法——一种资源分配拒绝策略。

1. 从银行贷款说起

算法的名字来自一个比喻。银行家拥有一笔周转资金，客户要求分期贷款。这里有一个关键前提：如果客户能够得到所有各期贷款，就一定能够归还贷款；否则就一定不能归还贷款。于是银行家应当谨慎地贷款，保证每个客户都能肯定得到后面的所有各期贷款，防止出现坏帐。

把角色一一对应过来，就是一个资源分配问题：

  • 操作系统——银行家；
  • 操作系统管理的资源——周转资金；
  • 进程——要求贷款的客户。

银行家不能把资金借到「看起来不够还」的地步，操作系统同样不能把资源分到「将来可能转不动」的地步。用「先算后给」代替「先给再救」，这就是银行家算法避免死锁的基本思想。

2. 系统模型

设系统有 m 类资源和 n 个进程。银行家算法要区分总量、已分配量、最大需求、剩余需求和当前可用量，不能把最大需求与剩余需求混作一个会变化的矩阵：

  • Total[j]：系统中第 j 类资源的总量；
  • Max[i,j]：进程 i 声明的第 j 类资源最大需求量，进程运行期间保持不变；
  • Allocation[i,j]：当前已分配给进程 i 的数量；
  • Need[i,j]：进程 i 还可能需要的数量，满足 Need = Max − Allocation；
  • Available[j]：当前可用数量，满足 Available = Total − Σ Allocation。

因此任何时刻都必须有 0 ≤ Allocation ≤ Max，且所有进程已分配量之和不能超过 Total。

进程 i 请求向量 Request[i] 时，先检查请求是否非负且不超过剩余需求，再检查是否不超过当前可用量。两项都满足后，才进行试探分配：

  • Allocation[i] 增加 Request[i]；
  • Need[i] 减少 Request[i]；
  • Available 减少 Request[i]；
  • Max 不变，因为它是进程预先声明的上限。

对试探后的状态运行安全性检查。若找到能让所有进程依次完成的安全序列，就正式接受请求；否则撤销试探分配，原状态保持不变。进程释放资源时，Allocation 相应减少、Available 相应增加，Need 则重新按 Max − Allocation 计算。

还有两条前提与原则：

  • 每个进程必须预先声明各类资源的最大需求，且 Max[i] ≤ Total；
  • 不安全状态不等于已经死锁，但系统不能再保证所有进程都能完成，因此请求只能在试探分配后仍安全时才接受。

3. 系统的安全状态

安全性检查从 Work = Available 开始，并把所有进程标记为未完成。反复寻找一个未完成且 Need[i] ≤ Work 的进程；假定它完成后释放已占有资源，令 Work = Work + Allocation[i]，再标记为完成。若最终所有进程都完成，记录下来的顺序就是安全序列；若再也找不到可完成的进程而仍有进程未完成，当前状态就是不安全的。这里比较的是 Need，而不是 Max，因为 Allocation 已经拿在进程手中。

因此每次请求都要先检查边界、试探更新 Allocation/Need/Available，再运行上述安全性检查：能找到安全序列才保留更新；找不到就完整回滚。银行家算法属于资源分配拒绝策略，它通过拒绝会破坏安全状态的请求来避免死锁。

反之，如果某个状态无论如何都找不到这样的推进顺序，它就是不安全状态。需要强调的是：不安全状态只是「有可能」死锁，并不是一定死锁——它意味着系统已经失去了「保证不发生死锁」的能力。

5. 银行家算法的缺点

  • 每个进程必须事先说明对各类资源的最大需求量。这是一个很强的要求：程序在运行前就要把一辈子要用的资源全报出来，实际中很难做到，而报得不准则整个算法失效；
  • 算法有些保守，总是考虑最坏情况。有时为了避免死锁，可能拒绝某一请求，即使这一请求实际上并不会导致死锁。过于谨慎和开销较大，是银行家算法的主要障碍——每次分配都要试算一遍安全序列，系统负担不轻。

本节小结

  • 银行家算法用银行贷款作比喻：操作系统是银行家，资源是周转资金，进程是要求分期贷款的客户；只有确信客户能还清，才把钱借出去；
  • 始终区分固定的 Max、当前 Allocation、剩余 Need 与 Available：Need = Max − Allocation，Available = Total − Σ Allocation；
  • 申请时必须先验证 Request ≤ Need、Request ≤ Available，并且试探分配后仍安全才会提交；
  • 安全性检查以 Available 为 Work，用 Need 判断进程能否完成，再把其 Allocation 加回 Work；找到全体进程的完成顺序才是安全状态；
  • 不安全状态不等于已经死锁，只表示不再有「保证不死锁」的能力；
  • 银行家算法的两大障碍：必须预先知道最大需求量，以及过于谨慎、开销较大。
